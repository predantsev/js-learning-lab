# Product requirements

Version: requirements baseline 3 (approved lesson design), 2026-09-30; accepted independent-review corrections incorporated. Source: approved product intent supplied to this bootstrap task. All statements below specify target behavior, not existing implementation. Technical recommendations live in DECISIONS.md and are not approved choices. Requirement IDs are stable; acceptance criteria are normative. Verification cases are in VERIFICATION.md.

## Provenance and authority

The approved course intent includes meaningful visuals, bounded analogies, delayed revisiting and usable accessible interactions; REQ-006, REQ-007 and REQ-031 retain their scope. Testable criteria elaborate that intent, not observed application behavior. The owner subsequently approved: contextual HTML/CSS within JavaScript, explicit stage runtimes and checkpoint protocols, continuation without native tooling, capstone switching through a separate project, and English canonical code/comments with localized example UI. See [Review resolution](reviews/REVIEW-RESOLUTION.md). DECISIONS.md separates settled behavior from engineering choices still to verify. REQ-025 remains a recommendation.

## Product boundary

Build a complete, highly interactive, local-first desktop course for absolute beginners and returning developers. Deliver one course; let experience change pacing through voluntary skipping, not a different curriculum. Teach with concise explanations, meaningful visuals and actual code producing observable UI/data changes. No production wishlist integration, cloud authentication requirement, paid AI tutor, mobile platform layout, or obligation to complete four capstones is in scope. These exclusions do not exclude React Native mobile-app development on a computer.

## Course and pacing

| ID | Requirement | Testable acceptance |
|---|---|---|
| REQ-001 | Course order is JavaScript, React, React Native, Node.js. | Navigation and prerequisite graph expose all four complete stages in exactly this order; no alternate beginner/expert track is needed to finish. |
| REQ-002 | Begin at absolute beginner level and support experienced returners. | First lessons explain code, values, running and errors without assumed programming knowledge; a short HTML/CSS bridge inside JavaScript teaches required markup, selectors, box/layout basics, forms and accessible labels before DOM/JSX work, without outside study; any lesson/topic has an “I know this / skip” action and optional brief self-check. |
| REQ-003 | Skip preserves learning continuity. | A skipped topic remains visibly skipped, revisitable, and distinct from passed self-check; unavailable native tooling does not block Node/later learning, and native tasks stay unperformed/skipped with provenance until revisited; advancing offers a suitable starter/checkpoint when prior project work is missing and never silently replaces learner files. |
| REQ-004 | Small resumable lessons. | After closing/restarting mid-exercise, restore lesson, active step, files, selection of capstone and relevant settings; proposed lesson size is 5–15 minutes excluding independent project work. Save status is visible. |
| REQ-005 | Use the full instructional loop. | Every instructional lesson has explanation, prediction, real run/change, focused independent practice and a capstone transfer task or explicit link to the next integration checkpoint; review/assessment lessons declare their different purpose. |
| REQ-006 | Difficult concepts receive meaningful visuals and bounded analogies. | Curriculum-tagged difficult concepts have a controllable step-through tied to actual code/data, text equivalent, analogy and limitation; visual changes explain the mechanism, not decoration. |
| REQ-007 | Mix retrieval, coding, debugging and delayed review. | Each curriculum unit has prediction/quiz, code writing, debugging and independent work with no required hints; a later lesson revisits at least one earlier concept without giving its answer upfront. Delayed review remains accessible after restart; automated due-date scheduling is optional. |
| REQ-008 | Complete target course has no placeholder stages. | Every curriculum unit and capstone checkpoint in CURRICULUM.md passes the content quality gate in CONTENT-DATA.md in both languages; no empty React, React Native or Node.js sections qualify as complete. |

## Capstones and working environments

| ID | Requirement | Testable acceptance |
|---|---|---|
| REQ-009 | Select one of four capstones at the start. | Choice lists only wishlist, planner, habit tracker and simple expense tracker; each follows the shared competency mapping, and completion of one suffices. Changing capstone creates a separate project/workspace, preserving old files and project-specific progress; general course evidence remains accessible, but new-project transfer/checkpoint completion is not fabricated. An educational wishlist uses original generic assets/data. |
| REQ-010 | Coherent progressive checkpoints. | Each selected project progresses from JavaScript to React to React Native to Node.js using the same domain model, learner files and history where applicable; platform-specific adapters/folders are explained, not unrelated replacement projects. Objectives, domain-independent components and contracts are reusable across options with small domain variants; a universal checkpoint generator is not mandated. |
| REQ-011 | Start in-course with editor/result side by side. | First coding exercises and capstone steps run inside the platform; useful multi-file examples allow file create/edit/select and accessible preview/console inspection. Desktop resizing retains usable editor and result. |
| REQ-012 | Guided export of the same project to VS Code. | At the documented transition checkpoint, export includes all current files, manifest, instructions and selected capstone; learner can open/install/run it locally and compare the same functionality; exports do not discard unsubmitted edits. |
| REQ-013 | Hybrid practice after transition. | Meaningful small exercises remain in-course across all four stages using the declared browser-executable concepts, labeled previews or verified isolated runtime; native/device and real-server tasks use guided local tooling. Stage runtime policy is in CURRICULUM.md; previews never substitute for local verification. After export, learner files in VS Code are authoritative; checkpoints supply separate starter/reference downloads, readable diffs and manual backup/merge instructions, with optional user-selected snapshot comparison. No automatic local replacement or bidirectional sync is implied; each local step includes prerequisites, exact instructions, expected results, troubleshooting and a non-destructive starter/checkpoint alternative. |
| REQ-014 | Honest native and server boundaries. | Each exercise labels its runtime and verification method; browser React Native concept previews explicitly lack native verification, native/emulator tasks run locally, and Node real-server tasks require an actual local process and HTTP request verification. Before Node, native networking uses bundled fixtures and/or a supplied minimal mock-service tool, not a learner-built backend. A learner without native tooling can complete Node integration with the web client while native evidence stays unperformed; product release still requires complete RN content and a verified supported native workflow. |

## Localization and support

| ID | Requirement | Testable acceptance |
|---|---|---|
| REQ-015 | Ukrainian default, full Ukrainian and English coverage. | A fresh profile opens Ukrainian; every required UI string, explanation, task, hint, authored feedback and glossary entry has reviewed translations; switching globally retains files/progress and active lesson. Canonical example identifiers and comments are English; authored example/capstone UI text follows the lesson language using shared logic/localized strings. Arbitrary learner code/comments are never rewritten on language change. |
| REQ-016 | Per-block alternate-language viewing in both directions. | Use a compact EN/UA control in the same canonical block; translate its heading, body, diagram labels and analogy in place. With global Ukrainian, inspect English and return without global change; repeat from English to Ukrainian for explanations/hints/tasks/glossary. Preserve other blocks, drafts, progress, disclosures, bookmarks and focus/context. |
| REQ-017 | Consistent natural technical glossary. | Terms such as props, state, hooks and closure retain appropriate English names, have contextual Ukrainian/English definitions, and use consistent references; definition is accessible by keyboard and hover without leaving the lesson. Optional expansion shows a small visual example. |
| REQ-018 | Voluntary progressive hints and separate solution. | A fresh/failing exercise hides all hints; deliberate reveal exposes nudge, then explanation, then a separately selected full solution; failure never auto-reveals a solution. Store levels viewed and solution viewed independently of completion. |
| REQ-019 | Actionable feedback preserves ownership. | Syntax, runtime and assertion failures identify relevant context, offer retry, and preserve learner files; authored guidance is localized, raw runtime diagnostics stay verbatim. Solution inspection does not overwrite editor content. |
| REQ-020 | Bookmark a specific block. | Save an explanation, example or exercise with a stable target; review collection opens that exact target, supports removal and persists restart; content updates resolve redirects or explain missing targets without losing the bookmark. |

## Execution, persistence and local distribution

| ID | Requirement | Testable acceptance |
|---|---|---|
| REQ-021 | Run real learner code outside platform state. | Modified learner code changes real output; isolation prevents access to parent storage/DOM, profile data, filesystem outside authorized project tooling, platform process privileges and credentials; attempted escape is tested at supported boundaries. |
| REQ-022 | Interrupt and recover runaway execution. | Infinite-loop fixture is stopped through a responsive platform control or declared timeout; editor and saved work survive, status explains termination, and rerun works in a fresh execution context. Early feasibility evidence includes a synchronous runaway DOM example with responsive control or responsive controller plus enforced timeout; an unsupported design is replaced or contained before exposing real learner execution, without substituting a fake runtime. |
| REQ-023 | Explicit resource and network policy. | Document allowed APIs, imports, capabilities, origins and resource limits per runtime; denied access has useful feedback. Core exercises execute offline after preparation; optional network tasks require explicit user action and are clearly labeled. |
| REQ-024 | Persist learner data locally with versioning. | Save platform-managed project/exercise files, active project/capstone, lesson/step progress, global and project-specific evidence, skip state, hint usage, bookmarks, review state and preferences (including selected visual style) atomically or recoverably; local VS Code files are saved/backed up by the guided local workflow, with no automatic synchronization; restart retrieves them. If storage is origin-bound, hostname/port changes require a stable-origin or explicit warning/recovery design so a fresh origin never silently suggests old work was deleted; origin-change behavior is tested before launch documentation recommends a fallback. Storage failures/quota errors warn accurately and keep unsaved code exportable. |
| REQ-025 | Proposed enhancement: portable backup/recovery. | Recommended implementation: export/import covering all learner data with schema version and checksum/validation; import previews replacement/merge behavior, rejects corrupt/newer unsupported data without changing originals, and round-trip restores a test profile. No secrets included. |
| REQ-026 | Keep runtime learner data out of public source. | Actual writable directories are documented and gitignored; fixture data is synthetic; public readiness review finds no learner records, personal notes, secrets or proprietary source. Browser storage backup files must be exported outside tracked paths. |
| REQ-027 | Clean-clone local setup is short and complete. | On each supported OS, documented prerequisites plus a short ordered install/start procedure launch a usable seeded course; no cloud account, paid API, secret, remote DB or external service required. Every mandatory asset/content file is bundled. Public clone/run needs no maintainer account, absolute machine path or sibling canon; license and asset-rights approval is a separate publication gate, not a cloud runtime dependency. |
| REQ-028 | Honest offline operation. | Disconnect network after documented initial preparation: core content, visuals, code runner, data save and review work; local tooling dependencies are cached/prepared as documented. Optional links/downloads clearly explain their internet need. |
| REQ-029 | Minimal appropriate persistence infrastructure. | If browser/file storage suffices, no mandatory DB is introduced; if a DB/backend is selected, setup initializes and seeds automatically, survives restart and documents safe migration and backup/restore with a failed-migration test. |
| REQ-030 | Explicit supported desktop environment. | Release docs name actual tested OS/browser versions, minimum viewport and tooling matrix; unsupported environments show actionable guidance. No claim of mobile platform adaptation or untested OS support. |

## Accessibility and failure states

| ID | Requirement | Testable acceptance |
|---|---|---|
| REQ-031 | Accessible interactions and learning visuals. | Complete a lesson, hints, bookmark, glossary, language switching and code execution using keyboard; focus is visible, announcements useful, labels clear, contrast adequate, and step-through has equivalent text with reduced-motion support. No hover-only information. |
| REQ-032 | Explicit non-destructive error states. | Missing/corrupt content, compile failure, runner crash/timeout, storage quota/corruption, import conflict, export failure and missing local tooling each show a distinct state, preserved work and recovery/retry path; no false saved/passed status. |
| REQ-033 | Transparent understanding evidence. | Navigation distinguishes base lesson states unseen, in-progress, skipped and completed, with demonstrated-understanding and exercise/transfer evidence shown independently; hint-assisted/solution-viewed evidence is visible without shaming. Passing a self-check can demonstrate its assessed concept but cannot fabricate project work. Global lesson/knowledge evidence is distinct from per-project transfer/checkpoint evidence; changing capstone does not erase either old-project evidence or general learning, nor pass the new project. |
| REQ-034 | Verifiable release rather than demo completion. | Release report links every requirement to recorded checks, curriculum coverage and actual environment; untested or unfinished work remains labeled partial/unconfirmed. M1 delivery alone cannot be reported as the whole course. |
| REQ-035 | Three interchangeable application visual styles with local preference persistence. | Offer Calm Studio (`calm-studio`), Editorial (`editorial`) and Dev workspace (`dev-workspace`); fresh data defaults to Calm Studio. Switching changes presentation only, preserving code, progress, hints, bookmarks, active context and global language. Save the application-wide stable style ID locally and restore on restart. Unknown/retired IDs use a documented fallback/migration to Calm Studio without clearing other data. All styles retain complete functional/content, Ukrainian/English and accessibility parity. Visual style is separate from light/dark appearance; no new appearance-mode requirement is implied. See [lesson design](design/LESSON-DESIGN.md). |

## Scope interpretation

Cloud sync, analytics, accounts, a hosted deployment, certificates, social features and AI feedback are not required. Separate local profiles, mastery presentation, review scheduling algorithm and backup UI are recommended designs to resolve before implementation. REQ-025 is a recommended enhancement, not an approved mandatory feature: adopt it explicitly or document the chosen portable recovery alternative and its limitations. Automated review scheduling and separate local profiles are also optional proposals. Mark conditional verification cases not adopted with rationale; do not turn them into unexplained release failures. Mandatory code/progress persistence, non-destructive failure recovery and honest evidence checks still apply.
